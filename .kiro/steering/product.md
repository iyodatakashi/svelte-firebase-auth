# Product Overview

`@14ch/svelte-firebase-auth` は、Firebase Authentication を使う Svelte アプリケーションのための認証ライブラリ。**認証の処理と画面**を提供し、組み込み側が同じものを書き直さずに済む状態にする。

**このリポジトリが作るのはライブラリであり、アプリケーションではない。** 最初の組み込み先は `markn`（マークダウンエディタ）だが、markn 専用ではない。同じ認証の画面と処理を必要とするプロジェクトが他にもあり、`md-editor` や `@14ch/svelte-ui` と同じく「別リポジトリで作って npm 越しに使う」形をとる。

**組み込み側の判断をライブラリへ持ち込まない。** ある特定のアプリだけに必要な分岐を内部に抱えると、次の組み込み先でそれが邪魔になる。アプリ固有の判断は、設定・コールバック・文言の差し替えとして**外へ出す**。

## Core Capabilities

- **認証ストア** — サインイン状態・利用者・正規化済みのメールアドレス・メールアドレスの確認状態を公開し、サインイン／登録／サインアウト／パスワードの変更／パスワードの再設定／確認メールの送信を行う
- **認証の画面** — サインイン・登録・パスワードの変更・パスワードの再設定。組み込み側は画面を書かずに済む
- **エラーの語彙** — Firebase のエラーコードを、**利用者への案内が分かれる粒度**へ畳んで返す。例外を投げず、判別可能な共用体で返す
- **文言の差し替え** — 既定の日本語を同梱し、組み込み側が項目単位で差し替えられる

## Target Use Cases

- Firebase Authentication のメールアドレスとパスワードによる認証を使う Svelte 5 のアプリケーション
- 利用者が自分で登録し、自分でパスワードを管理する（招待制ではない）アプリケーション
- メールアドレスの確認を、アプリを使うための条件として扱うアプリケーション

## Value Proposition

Firebase Auth の呼び出しは各アプリで似た形になり、画面もほぼ同じものが書かれる。それを1箇所に集め、**アプリ側には遷移と到達の判断だけを残す**。アプリが増えるほど効く。

## 担当しないこと

境界を曖昧にすると、ライブラリが特定のアプリの形に固まって再利用できなくなる。以下は**組み込み側の担当**であり、ライブラリは持たない。

- **Firebase の初期化** — `Auth` インスタンスを外から受け取る
- **遷移とルーティング** — SvelteKit を含む特定のフレームワークのルーティングに依存しない。完了・失敗をコールバックで返し、遷移は組み込み側が行う
- **到達ガード** — 未サインイン／未確認の利用者をどこへ送るかは、アプリの画面構成の問題
- **Firestore とアクセス制御** — 認証だけを担当する。データの読み書きに触れない
- **メールの送信経路と到達性** — Firebase の既定の経路を使う。送信元ドメインや SPF / DKIM / DMARC の設定は組み込み側の運用

## 備えないもの

- **メールリンクによるサインイン** — 自由登録とパスワードがある以上、パスワードを作らずに入る経路は不要。加えてメールの到達性に依存する経路は行き止まりを作る
- **メールアドレスの変更**
- **外部の認証プロバイダ（Google / Apple などのソーシャルログイン）** — 現時点で要求が無いだけであり、後続で加えうる。「対象外」ではない
- **二要素認証・アカウントの削除** — 現時点で要求が無い

## まだ決めていないもの

- **メールアドレスの確認待ち画面をライブラリが持つか。** 確認待ちの状態そのものは Firebase Auth の利用者が持つ事実であり、画面の中身（再送・別アドレスでの登録し直し・サインアウト）もアプリに依らない。一方で「確認済みでなければ使わせない」という判断は組み込み側のものである。最初の spec で決める
- **公開する画面の粒度。** 画面をまるごと渡す形だけで足りるのか、ストアと部品を組み合わせる余地も要るのか。最初の組み込み（markn）で見極める
