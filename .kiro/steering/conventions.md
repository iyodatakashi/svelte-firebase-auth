# Conventions（作業・コードの恒久ルール）

このプロジェクトで守る作業規約。個別のやり取りで指摘・合意された内容を集約する。`markn` / `md-editor` の同名の規約に準拠し、このライブラリに固有の事情だけを足す。

**コードの書き方そのものは `structure.md`（命名・型の置き場所・import・BEM・共通化の判断）と `tech.md`（型安全・アロー関数・書式・テスト）にある。** ここに重複させない。コードを書く前に、まず `structure.md`「型定義の規約」を照合する。

## 説明の仕方

- **相手が知らない可能性のある用語を、説明なしに使わない。** ライブラリの API 名（`onAuthStateChanged`、`$bindable`、`Snippet` など）や仕様上の造語を、当然わかる前提で並べない。初出では一言で定義してから使う。
- **まず「組み込み側の開発者・利用者から見て何が起きるか」で説明する。** 内部の名前や仕組みは、それが必要になったときだけ出す。「確認を済ませても画面が先へ進まない」と言えば伝わるものを、「`onAuthStateChanged` は `emailVerified` の変化で発火しない」と書かない。
- **説明が伝わらなかったら、言い換えではなく前提から説明し直す。** 同じ構造の説明を語彙だけ変えて繰り返さない。

## スコープの扱い

- **「初版に含めない」と「対象外」を区別して書く。** 後から加えると分かっているものを「スコープ外」と書かない。書いた除外リストは、後日その機能に着手するときに「スコープ外だ」と押し戻す根拠として使われ、開発を妨げる。将来加えるものは「後続で加えうる（対象外ではない）」と明記し、設計時は後から載せられる形を選ぶ。
  - 該当するもの（→ `product.md`）: 外部の認証プロバイダ（Google / Apple などのソーシャルログイン）、メールの送信経路の差し替えの実装
  - 逆に、本当に要求が無いものは「現時点で要求が無い」と書く。これは「やらないと決めた」ではなく「まだ要求されていない」の意味である。
- **指示に無い制約を、決定事項として書かない。** 範囲を絞る仮定を置くのは構わないが、それは「筆者が置いた仮定（未承認）」と分かる形にする。仮定を既定事実として書くと、後から誰も根拠を辿れなくなる。何を作らないかを決めるのは依頼者であり、書き手ではない。

## 組み込み側の spec を、制約として扱わない

このライブラリは組み込み先（現在は `markn`）より後に作られる。組み込み側の spec には、このライブラリの公開面が先に書かれていることがある。

- **組み込み側に書かれた契約は、実需を示す出発点であって制約ではない。** 仕様として妥当かどうかを、こちらで判断し直す。
- **こちらで決めた結果は、組み込み側へ返す。** 食い違いを放置すると、どちらが正なのか分からない状態が残る。返す事項は spec に明記する。
- **組み込み側の都合による分岐を、ライブラリの内部に持ち込まない。** 設定・コールバック・文言の差し替えとして外へ出す（→ `product.md`）。

## spec と、作りながらの判断

- **spec は事前の想定であって、作って見たうえでの判断がそれに優先する。** 見た目や操作感を詰めている最中に当初の決め事と食い違うのは当たり前であり、その食い違いを理由に手を止めない。
- **「requirements に反します」を判断の理由にしない。** 反していること自体は問題ではない。問題は、変えた理由が残らないことだけである。
- **spec は追いかけて直す。** 実装が固まった時点で requirements / design を書き換える。**番号は動かさない**（tasks.md や design.md の参照がずれるため）。既存の項目の文言を書き換えるか、末尾に足す。

## テストの由来

- **受け入れ基準（テスト）は `requirements.md` から引く。`design.md` から導出しない。** 設計に要件からの逸脱が入り込んだとき、設計由来のテストはその逸脱を受け継ぎ、**要件を満たさないまま緑になる**。テストが逸脱を検出する装置ではなく、逸脱を固定する装置になる。
- **適用**: 各テストに対応する要件の項番を書き、要件の文面をそのまま受け入れ条件にする。テストが書けない・書くと赤になるなら、疑うのは要件ではなく設計と実装である。

## Firebase

- **モックで済ませたことを、検証済みとしない。** モックが確かめるのは呼び出しの形だけであり、そこに書かれた応答は書き手の想定である。想定が外れていればテストは緑のまま壊れる。Firebase の実際の振る舞いに依存する箇所は、使える手段で一度は実物に当てる（→ `tech.md`）。
- **Firebase のエラーコードを、そのまま組み込み側へ透過させない。** 利用者への案内が分かれる粒度へ畳む。畳めない事情が出てきたら、語彙を増やすことを検討する。コードを露出させて回避しない。

## `@14ch/svelte-ui` との境界

- **部品が足りないときに、こちら側で回避しない。** ブラウザ標準の UI で代替したり、同じ役割の部品を自前で書いたりしない。`@14ch/svelte-ui` 側の課題として扱う（→ `tech.md`）。
- **ライブラリ独自のパレットを持たない。** 意匠の値はトークン（`--svelte-ui-*`）を参照する。組み込み側のテーマに従うため。

## 決定の進め方

- **合意していないものを、合意済みとして扱わない。** 複数の論点をまとめて提案した場合、決着したのは明示的に同意を得たものだけ。他の論点を「ついでに」反映しない。
- **決定を要する箇所は、選択肢と推奨をセットで出す。** 判断の根拠（何が失われ、何が得られるか）を添える。自分の推奨だけを書いて確認を省かない。
- **自分の提案が却下されたら、理由を確認してから次の案を出す。** 理由を推測して別案を出すと、同じ的外れを繰り返す。

## 記録

- **決定と、その理由・棄却した案を spec に残す。** 後から同じ議論を繰り返さないため。`research.md` の Design Decisions に「採らなかった案とその理由」まで書く。
- **プロジェクトの知識・規約は必ずリポジトリ内に書く。** `~/.claude/` 配下の私的メモリに保存しない（チーム非共有・リポジトリ外で、記録として機能しないため）。
- **`README.md` は英語で書く。** spec と steering は日本語のままでよい。

## 公開面の変更

- **公開面（`src/lib/index.ts`）に export されていないものは内部実装であり、いつ変えてもよい。** 逆に、export したものの変更は組み込み側の再検証の契機になる。
- **型・エラーの語彙・画面の props の変更は破壊的変更として扱う**（→ `structure.md`「公開面」）。とくに `AuthErrorKind` の増減は、組み込み側の文言の網羅に波及する。
- **迷ったら公開しない。** 足りなければ後から足せるが、出したものは引っ込められない。

## コミット（厳守）

- **指示なくコミットしない。** テストが緑でも、自分で動作を確かめても、それは「意図どおり動く」の確認でしかない。**完了かどうかを決めるのは依頼者**であり、自分の検証をその代わりに置かない。
- **コミットするのは、指示を受けた時点で存在した変更だけ。** 指示の範囲は「そのターンのあいだ」ではなく「そのとき手元にあった変更」で区切る。作業中に生まれた変更はコミットせず、未コミットのまま報告する。
- **「コミットしますか」と聞くのも行わない。** 提案も打診もしない。指示が無ければ何も言わずに止まる。
- **`--no-verify` / `--no-gpg-sign` を使わない。**

**md-editor では、この規約に反したコミットが実際に行われた**（2026-08-08）。文章の規約は、立ち止まって照合したときだけ働く。惰性で通り抜けることを前提に、手を動かす前に照合する。

## ブランチの運用（git-flow）

`markn` / `md-editor` と同じ運用を採る。**このリポジトリはまだ git 管理下に無い。初期化した時点でこの表に従う。**

| ブランチ         | 役割                                           | 分岐元    | 統合先              |
| ---------------- | ---------------------------------------------- | --------- | ------------------- |
| `main`           | 公開した版だけを置く。ここへ直接コミットしない | —         | —                   |
| `develop`        | 統合先。日々の作業はここへ集まる               | `main`    | —                   |
| `feature/<名前>` | 機能の追加・変更                               | `develop` | `develop`           |
| `bugfix/<名前>`  | `develop` 上の不具合修正                       | `develop` | `develop`           |
| `release/<版>`   | 公開の準備（版番号の確定・最終確認）           | `develop` | `main` と `develop` |
| `hotfix/<版>`    | 公開済みの版の緊急修正                         | `main`    | `main` と `develop` |

- **版のタグは `v` を付ける**（例: `v0.1.0`）。`main` へ入れた時点で打つ
- **`feature` の統合は早送りにしない**（`--no-ff`）。まとまりが履歴に残らなくなるため
- **既定の作業ブランチは `develop`。** `main` へ直接コミットしない
