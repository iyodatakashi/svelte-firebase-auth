# Gap Analysis

**対象**: `sveltekit-routing-and-guard`
**性質**: 既存コードの作り替え（brownfield）。新規機能ではなく、**公開面の方針転換**
**注意**: 本分析の時点で requirements は未承認（`approvals.requirements.approved: false`）。分析結果は要件の修正に用いてよい

## Summary

- **ストア層は無傷で流用できる。** `AuthStore.stage` は本 spec のガードがそのまま消費する形になっており、追加は不要
- **書き替えの中心は画面5つとそのテスト（601行）**、およびショーケース・E2E・README
- **`$app/*` は SvelteKit の Vite プラグインが解決する仮想モジュール**であり、`svelte-package` は `dist` へそのまま残す。配布は成立する
- **`goto` はルーター無しの環境で例外を投げ、`page.url` は空になる。** コンポーネントのテストに影響する。**ガードが URL を内部で読むか、引数で受けるかが最大の設計論点**
- 規模 **M**、リスク **Medium**。未知の技術は無いが、公開面の破壊的変更と、テストの作り替えが広い

## 1. Current State Investigation

### 配布物の構成（`src/lib/`）

| 層         | ファイル                                          | 本 spec の影響                                                   |
| ---------- | ------------------------------------------------- | ---------------------------------------------------------------- |
| models     | `auth.types.ts` / `auth.ts` / `auth.constants.ts` | **型のみ変更**（props からコールバックを外し、経路の設定を足す） |
| messages   | `ja.ts` / `authErrorMessage.ts`                   | **影響なし**                                                     |
| stores     | `auth.svelte.ts`（236行）                         | **影響なし。`stage` をガードが消費する**                         |
| components | 5画面（各 130〜170行）                            | **全面的に書き替え**                                             |
| index      | `index.ts`                                        | 公開する値の増減                                                 |

### 依存の向きと規約（`structure.md` / `tech.md`）

- `models → messages → components`、`models → stores → components` の一方向
- **`components` は `stores` を型としてのみ参照し、実体は props で受け取る**
- **Firebase Auth の呼び出しは `stores/` に集約**（画面は `firebase/auth` を import しない）
- 例外を投げず、失敗は戻り値で返す

**本 spec が加えるのは `$app/*` への依存だけ**であり、上記の向きは崩れない。ただし `tech.md`「`$app/*` を import しない」に**正面から反する**ため、規則の置き換えが前提になる（要件 7-1）。

### テストの配置と方式

| 区分                            | 対象                                 | 行数    |
| ------------------------------- | ------------------------------------ | ------- |
| `server`（node）                | models / messages / stores（モック） | 818     |
| `client`（Playwright ブラウザ） | 画面5つ                              | **601** |
| `emulator`（node）              | 実 Firebase                          | 約 190  |
| E2E（Playwright）               | ショーケース                         | 74      |

**画面のテストは 5 ファイルすべてがコールバックの呼び出しを検証している**（各ファイル 10〜15 箇所）。コールバックを廃すると、この 601 行は**検証の対象そのものが変わる**。

### 統合点

- **`AuthStore.stage`** — `unresolved` / `signed-out` / `email-unverified` / `ready`。**ガードが読む値は既に揃っている**
- **`AuthConfig`** — `selfRegistration` / `emailVerification` / `continueUrl`。ここへ経路を足す
- **`AuthBaseProps`** — `store` / `messages?` / `header?`。ここは残る

### Research Needed

1. **ガードが現在の URL をどう得るか。** `$app/state` の `page` を内部で読むと、コンポーネント／ユニットのテストで URL が空になる。**引数で受ける設計なら純関数として試験できる**
2. **戻り先の保持先。** URL のクエリ（再読み込みに耐える・オープンリダイレクトの検査が要る）か、モジュール内の状態（再読み込みで消える）か
3. **ガードを置く場所。** ルートの `+layout.svelte` の `$effect` か、`+layout.ts` の `load` で `redirect()` を投げるか。後者は SSR でも働くが、**Firebase の状態はサーバに無い**ため実質クライアント限定になる（要件 4-7 と整合するか要確認）
4. **確認待ちを跨いだ戻り先の保持**（要件 5-5）。登録 → 確認待ち → 確認完了の間、どこに保持するか
5. **`goto` の `replaceState`。** ガードによる振り替えを履歴に残すと、戻るボタンで振り替え前へ戻り、再び振り替えられる

## 3. Implementation Approach Options

### Option A: 既存の画面を拡張する（コールバックを `goto` に置き換える）

5画面の props からコールバックを外し、その場で `goto(config.routes.x)` を呼ぶ。ガードは新規に1つ作る。

- ✅ 新規ファイルが最小（ガードのみ）。画面の構造は変わらない
- ✅ 変更が読みやすく、既存の振る舞い（入力・エラー・処理中）に手が入らない
- ❌ 画面が `$app/navigation` を直接持つため、**5つのテストすべてがモックを要する**
- ❌ 画面が経路の知識を持つ

### Option B: 遷移を1箇所へ集める（画面は「意図」を伝える）

画面は `goto` を直接呼ばず、遷移を担う小さなモジュール（例: 認証の遷移を司る関数群）へ「サインインへ」「再設定へ」といった意図を渡す。そこだけが `$app/navigation` と経路の設定を知る。

- ✅ **`$app/*` を触るファイルが1つに閉じる。** 画面のテストはその1つを差し替えるだけで済む
- ✅ 経路の知識が1箇所。要件 2-2（画面とガードが同じ値を使う）が構造で保証される
- ✅ ガードと画面が同じ遷移の口を使う
- ❌ 間接が1段増える。「過剰な抽象化をしない」との兼ね合いの判断が要る
- ❌ 画面から遷移までの経路が読み取りにくくなる可能性

### Option C: 段階の遷移はガード、導線の遷移は画面（Option A + B の切り分け）

要件が既に採っている切り分けをそのまま構造にする。**完了（段階が変わる）はガードだけが扱い**、**導線（段階が変わらない）は画面が `goto` する**。経路の設定は両者が同じ設定オブジェクトから読む。

- ✅ 要件 3 の注（完了はガード、導線は画面）と一対一で対応する
- ✅ ガードが唯一の「判定 → 遷移」であり、二重化しない
- ❌ 画面に `$app/navigation` が残るため、Option A と同じテストのモックが要る
- ❌ 「どちらが遷移するか」を画面ごとに判断する必要がある

**論点**: Option B は、**ちょうど今回の方針転換で退けた「利用者の実在しない抽象」に見える恐れがある**。ただし B の動機は差し替えではなく**テスト容易性と経路の一元化**であり、実在する問題（`goto` が例外を投げる・`page.url` が空）に対応している。この区別を design で明示的に判断する必要がある。

## 4. Implementation Complexity & Risk

| 項目       | 評価            | 根拠                                                                                                                                                         |
| ---------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Effort** | **M（3〜7日）** | 未知の技術は無く、ストア層は無傷。ただし画面5つ・テスト601行・ショーケース・E2E・README の作り替えが同時に必要                                               |
| **Risk**   | **Medium**      | 公開面の破壊的変更だが**組み込み先が無く実害が無い**。技術的な未知は `page.url` の扱いと戻り先の保持先に限られ、いずれも実地に確認済みか design で決められる |

**リスクを下げている事実**

- 公開前（v0.1.0 未リリース）で組み込み先が無い
- `stage` が既にあり、ガードの判定ロジックを新たに考える必要が無い
- models / messages / stores のテスト 818 行は**そのまま通る見込み**（回帰の検出網が残る）

**リスクを上げている事実**

- 画面のテスト 601 行は検証の対象が変わるため、**回帰の検出網が一時的に薄くなる**
- E2E がショーケースの作り替えに引きずられ、同時に落ちる

## 5. Recommendations for Design Phase

### 優先して決めること

1. **ガードが URL を得る方法**（Research 1）。テスト容易性を左右する。**引数で受ける形を第一候補として検討する**
2. **Option A / B / C の選択。** 判断基準は「`$app/*` を触る箇所をいくつにするか」。**間接を足す理由がテスト容易性と経路の一元化であることを、記録に残す**
3. **戻り先の保持先**（Research 2）。URL のクエリなら、要件 5-4（同一オリジンの検査）が必須になる
4. **ガードを置く場所**（Research 3）と `replaceState` の扱い（Research 5）

### 進め方の提案

**画面のテストが同時に落ちる期間を短くする。** ストア層とガードを先に作り、ガードだけで到達の振り替えを E2E で確かめられる状態にしてから、画面のコールバックを外す順序が取れる。

### 要件へ返す論点

- **要件 4-7（ブラウザでのみ働く）と Research 3 の整合。** `+layout.ts` の `load` で `redirect()` を使う案は、SSR でも動く形に見えるが Firebase の状態がサーバに無いため実質クライアント限定になる。要件の文面が実装の選択肢を過度に狭めていないか、design で確認する
- **要件 5-5（確認を終えるまで戻り先を失わない）** は、保持先の選択（Research 2）に強く依存する。モジュール内の状態では再読み込みで失われるため、この要件が保持先を実質的に決めている可能性がある
