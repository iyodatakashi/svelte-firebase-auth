# Requirements Document

## Project Description (Input)

SvelteKit を前提にして、認証の遷移と到達ガードをライブラリ側へ移す。

### 背景と決定

`@14ch/svelte-firebase-auth` は現在、特定のフレームワークのルーティングに依存しない設計になっている（`tech.md`「SvelteKit に依存しない」・`$app/*` を import しない・遷移はコールバックで組み込み側へ返す）。

依頼者から「実質 SvelteKit しか使わない。SvelteKit 限定になるのは問題ない」との判断が示された。framework 非依存は、**利用者が実在しない抽象**であり、`research.md` で ports & adapters を退けたのと同じ理由（差し替える相手が実在しない・抽象化の層が増える）で維持する根拠を失っている。

**入口は1つのまま SvelteKit ネイティブにする。** `/sveltekit` のような第2の入口は作らない（公開面・文書・「中核か層か」の判断が二重になり、恒久的な負担になるため）。

### この spec で作るもの

- **コンポーネントが自分で遷移する。** 現在 5画面が持つコールバック13本の配線を、組み込み側から無くす
- **認証の経路の設定** — サインイン・登録・確認待ち・パスワードの再設定・完了後の行き先を設定で受け取る
- **到達ガード** — `AuthStore.stage`（`unresolved` / `signed-out` / `email-unverified` / `ready`）を読んで遷移する仕組みをライブラリが提供する。組み込み側が同じ判定と遷移を書き直さない
- **サインイン後に元のページへ戻す（戻り先の保持）** — 現在は URL を読めないため未実装
- **ショーケースを本物のルートへ** — 画面切り替えの仕掛けを廃し、SvelteKit の経路として組む

### 組み込み側（markn）へ返す事項

**画面の props の変更を破壊的変更として扱う。** 本 spec の実装により、markn 側の `AuthModuleContract` に整合しない箇所が残る。markn 側で扱う。

- **画面ごとの props の型を廃止した。** `SignInProps` / `SignUpProps` / `VerifyEmailProps` / `PasswordChangeProps` / `PasswordResetProps` は無くなり、5画面すべてが `AuthBaseProps`（`store` / `messages?`）だけを受け取る
- **題字と名乗りの差し込み口を廃止した。** `header?: Snippet` の props と、題字の文言 `signInTitle` / `signUpTitle` / `verifyEmailTitle` / `passwordChangeTitle` / `passwordResetTitle` が無くなった。**見出しは markn 側のページが置く**（→ `auth-store-and-screens` 要件 9-6 の注）
- **コールバックの props 13 本が公開面から消えた。** `onSignedIn` / `onSignedUp` / `onVerified` / `onChanged` / `onRequested` / `onSignOut` / `onCancel` / `onRequestSignIn` / `onRequestSignUp` / `onRequestPasswordReset` / `onRequestSignUpWithAnotherEmail` — markn 側の薄いアダプタからこれらの配線を落とす
- **代わりに `onCompleted?: () => void` が5画面共通で入った。** 省略できる。**遷移は行わない**。パスワードの変更と再設定メールの送信は段階を変えないため、そこで何をするかを決められるのは markn 側だけである。渡さない場合の既定（完了の表示と戻る導線）は用意してある
- **`AuthConfig` に `routes` が必須の項目として加わった。** サインイン・登録・確認待ち・パスワードの再設定の経路と、認証を終えた利用者の既定の行き先を渡す
- **段階から遷移への対応づけを、markn 側で書かない。** 根の `+layout.svelte` で `AuthGate` を1つ置く。**パスワードの変更の経路は認証の経路に含めない**（含めると、サインイン済みの利用者が追い出される）
- **`@sveltejs/kit` が peer の依存になった。** markn は SvelteKit のアプリであり、追加の作業は無い
- **公開前（v0.1.0 未リリース）であり、実害のある組み込み先は無い**

## Introduction

`auth-store-and-screens` で作った認証ストアと5画面は、遷移を持たず、完了と遷移の要求をコールバックで組み込み側へ返す形になっている。この形は framework 非依存のために選ばれたが、**その利用者は実在しない**。結果として、組み込み側は 13 本のコールバックの配線と、`stage` から遷移への対応づけを、プロジェクトごとに書き直すことになる。

本 spec は前提を SvelteKit に固定し、**遷移と到達ガードをライブラリ側へ移す**。組み込み側に残るのは、Firebase の初期化・経路の設定・アクセス制御だけになる。

### EARS の主語

- **the 認証ライブラリ** — パッケージとして公開する面全体の性質。配布・設定・型
- **the 認証ストア** — `createAuthStore` が返すもの
- **the 到達ガード** — 認証の段階に応じて到達を振り替える仕組み
- **the サインイン画面 / 登録画面 / 確認待ち画面 / パスワード変更画面 / パスワード再設定画面** — 個々の画面。**the 各画面** は5画面すべてに共通する要求を指す

### 依頼者が決めたこと

- **SvelteKit 限定にしてよい。** framework 非依存は維持しない
- **入口は1つに保つ。** SvelteKit 向けの第2の入口を作らない
- **判定だけでなく遷移もライブラリが持つ。** 組み込み側が同じ仕組みを毎回作らずに済ませる

### 筆者が置いた仮定（未承認）

依頼者の指示に含まれておらず、要件を書くために筆者が置いた仮定。承認されていないため、必要なら差し替えてよい。

1. **完了時の遷移は画面ではなく到達ガードが行う**（要件 3 の注、要件 4）。サインイン・登録・確認の完了はいずれも認証の段階を変えるため、段階を見ているガードが動かせば足りる。画面にも同じ判断を書くと二重になる
2. **画面が自ら行う遷移は、段階を変えない導線だけとする**（要件 3）。「パスワードの再設定へ」「サインインへ戻る」など
3. **遷移の要求を返すコールバックの props は残さない**（要件 3-7）。「念のため差し替え口を残す」ことは、利用者の実在しない抽象を作ることであり、本 spec の出発点と矛盾する。**完了を返すコールバックは実装中に必要になったため足した**（省略可能・非破壊。→ 要件 3-7 の注）
4. **戻り先は同一オリジンの経路に限る**（要件 5-4）。外部の URL を戻り先にできると、サインインの画面を踏み台にした誘導が成立する
5. **到達ガードはブラウザでのみ働く**（要件 4-7）。Firebase Authentication の状態はブラウザにあり、サーバ側では判定できない
6. **パスワードの変更の経路は「認証の経路」に含めない**（要件 4-5）。サインイン済みの利用者が使う機能であり、認証の経路として扱うとガードが利用者を追い出す

## Boundary Context

- **In scope**: 認証の経路の設定、5画面が自ら行う遷移、到達ガード、サインイン後の戻り先の保持と復帰、`@sveltejs/kit` の peer 依存の宣言、ショーケースの経路化、README の書き換え、`tech.md`「SvelteKit に依存しない」の置き換え、`auth-store-and-screens` の要件 1-2 / 9-3 の書き換え
- **Out of scope**: Firebase の初期化、Firestore とアクセス制御、認証の画面の中身（入力・検証・文言・エラーの語彙）、メールの送信経路、サーバ側のセッション検証（Admin SDK を要するため）
- **後続で加えうる（対象外ではない）**: 経路以外の遷移の方法（差し替え・モーダル）
- **実装中に In scope へ入れた**: 画面の完了を組み込み側が知るための省略可能なコールバック（`onCompleted`）。当初は「後続で加えうる」としていたが、段階を変えない完了で組み込み側が何もできなくなるため、本 spec で足した
- **変わらないもの**（`auth-store-and-screens` から引き継ぎ、本 spec では触れない）:
  - Firebase の初期化は組み込み側が行い、`Auth` を受け取る
  - 認証以外の Firebase の機能に触れない
  - エラーの語彙・文言の差し替え・`normalizeEmail`・確認状態の取り直し
  - **画面の出し分けを理由にアクセス制御を緩めない**
- **Adjacent expectations**:
  - **`auth-store-and-screens`** — 本 spec は同 spec の要件 1-2（ルーティングに依存しない）と 9-3（遷移をコールバックで返す）を**置き換える**。同 spec 側を書き換える
  - **`tech.md`「SvelteKit に依存しない」** — 規則が引かれた理由（SvelteKit 以外のアプリで使えなくなる）が前提ごと変わったため、置き換える
  - **`markn`** — 最初の組み込み先。画面の props とコールバックの契約が変わるため、`AuthModuleContract` に返す

## Requirements

### Requirement 1: SvelteKit を前提とする配布と公開面

**Objective:** 開発者として、SvelteKit のアプリに認証を入れてすぐ動かしたい。遷移の配線を毎回書かずに済ませるため

#### Acceptance Criteria

1. The 認証ライブラリ shall `@sveltejs/kit` を peer の依存として宣言し、実体を自身で抱えない
2. The 認証ライブラリ shall SvelteKit のルーティングを用いて遷移を自身で行う
3. The 認証ライブラリ shall 公開面を単一の入口に保ち、SvelteKit を前提とする機能を別の入口へ分けない
4. The 認証ライブラリ shall 到達ガードを、組み込み側が1箇所で有効にできる形で提供する
5. The 認証ライブラリ shall 公開する値に対応する型を公開面から提供し、組み込み側が型を書けない状態にしない

**注**: 3 は、公開面・手引き・「中核か層か」の判断が二重になることを避けるための要求である。SvelteKit 以外の組み込み先が現れた時点で中核を抜き出す（→ 変更の記録）。

### Requirement 2: 認証の経路の設定

**Objective:** 組み込み側の開発者として、自分のアプリの URL 構成に認証の画面を置きたい。ライブラリに経路を決めつけられないため

#### Acceptance Criteria

1. The 認証ライブラリ shall サインイン・登録・確認待ち・パスワードの再設定の経路と、認証を終えた利用者の既定の行き先を、組み込み側の設定として受け取る
2. The 認証ライブラリ shall 設定された経路を、画面が行う遷移と到達ガードの双方で同じ値として用いる
3. Where 自由登録が許可されていないとき, the 認証ライブラリ shall 登録の経路への遷移を行わない
4. If 設定された経路が与えられていないとき, then the 認証ライブラリ shall 型検査の段階で組み込み側に示す
5. The 認証ライブラリ shall 現在の経路が設定された経路のいずれであるかを、問い合わせ文字列に左右されずに判定する

**注**: 2 は、経路の出所を1つにするための要求である。画面とガードが別々に経路を持つと、片方だけを変えたときに到達できない画面ができる。

**注**: 4 は、経路が欠けた状態を実行時の分岐として抱え込まないための要求である（→ `CLAUDE.md`「欠損データを許容する分岐を残さない」）。

**注**: 5 は、経路の一致の判定を実装者の解釈に委ねないための要求である。問い合わせ文字列や末尾のスラッシュで一致が崩れると、**振り替え先がふたたび振り替えの対象になり遷移が止まらない**。

### Requirement 3: 画面が自ら行う遷移

**Objective:** 組み込み側の開発者として、認証の画面を置くだけで導線がつながる状態にしたい。画面どうしの行き来を自分で配線しないため

#### Acceptance Criteria

1. When 利用者がパスワードの再設定を要求したとき, the サインイン画面 shall 再設定の経路へ遷移する
2. Where 自由登録が許可されているとき, when 利用者が登録を要求したとき, the サインイン画面 shall 登録の経路へ遷移する
3. When 利用者がサインインへ戻ることを要求したとき, the 登録画面 shall サインインの経路へ遷移する
4. When 利用者が別のメールアドレスでの登録し直しを要求したとき, the 確認待ち画面 shall サインアウトしたうえで登録の経路へ遷移する
5. When 利用者が変更を取りやめたとき, the パスワード変更画面 shall 既定の行き先へ遷移する
6. When 利用者がサインインへ戻ることを要求したとき, the パスワード再設定画面 shall サインインの経路へ遷移する
7. The 各画面 shall 遷移の要求を組み込み側へ返すコールバックの props を持たず、完了を返す省略可能なコールバックだけを持つ
8. When パスワードの変更が完了したとき, the パスワード変更画面 shall 変更の操作を出さず、既定の行き先へ戻る導線だけを示す

**注**: サインイン・登録・確認・サインアウトの**完了**時の遷移は、この要件に含まれない。いずれも認証の段階を変えるため、段階を見ている到達ガードが行う（要件 4、→ 筆者が置いた仮定 1）。画面にも同じ判断を書くと、判定が2箇所に増える。

**注**: 8 は実装中に足した。「完了時の遷移は到達の制御に任せる」という決めごとの理由は、**その完了が認証の段階を変えるから**である。パスワードの変更は段階を変えないため、ガードは動かない。理由の射程を確かめずに結論だけを当てはめた結果、変更を終えた利用者が、押せる意味のない操作だけが並ぶ画面に取り残されていた。**完了したら、次の一手を1つだけ出す。**

**注**: 7 は、遷移をライブラリが持つという決定を、公開面から曖昧さなく読み取れるようにするための要求である。**遷移の要求**を返すコールバックは持たない。

**注**: 7 の「完了を返すコールバック」は実装中に足した。当初は完了のコールバックも持たない形にしていたが、**それでは組み込み側が完了時に何もできない**。段階を変える完了はガードが動かすが、段階を変えない完了（パスワードの変更・再設定メールの送信）では誰も動かず、行き先を決める手段が組み込み側から失われていた。省略可能な props を後から足すのは非破壊であり、Boundary Context に「後続で加えうる」と書いた項目そのものである（→ 筆者が置いた仮定 3）。

### Requirement 4: 到達ガード

**Objective:** 組み込み側の開発者として、未サインインや未確認の利用者を然るべき画面へ送る仕組みを、プロジェクトごとに書き直したくない。同じ判定と遷移が組み込み先の数だけ増えるため

#### Acceptance Criteria

1. While 初回の認証状態の判定が完了していないとき, the 到達ガード shall 遷移を行わない
2. While 利用者がサインインしていないとき, the 到達ガード shall サインイン・登録・パスワードの再設定の経路への到達を許し、それ以外の経路への到達をサインインの経路へ振り替える
3. While 利用者がサインイン済みでメールアドレスの確認が済んでいないとき, the 到達ガード shall 確認待ちの経路への到達を許し、それ以外の経路への到達を確認待ちの経路へ振り替える
4. While 利用者が組み込み先の求める条件を満たしているとき, the 到達ガード shall サインイン・登録・パスワードの再設定・確認待ちの経路への到達を、既定の行き先または保持している戻り先へ振り替える
5. While 利用者が組み込み先の求める条件を満たしているとき, the 到達ガード shall それ以外の経路への到達を妨げない
6. When 認証の段階が変化したとき, the 到達ガード shall 変化した後の段階に応じて到達を振り替える
7. The 到達ガード shall ブラウザでのみ働き、サーバ側の描画では遷移を行わない
8. While 初回の認証状態の判定が完了していないとき, the 到達ガード shall 保護された経路の内容を描画させない

**注**: 2 と 3 が「その段階のための経路」を許すのは、振り替え先が振り替えの対象になって遷移が止まらなくなることを防ぐためである。

**注**: 4 は、サインイン済みの利用者がサインインの画面に留まらないための要求である。5 と合わせて、**パスワードの変更の経路は振り替えの対象にならない**（→ 筆者が置いた仮定 6）。

**注**: 6 は、到達の判断を状態から導くための要求である。サインインの完了時に一度だけ振り替える形にすると、既にサインイン済みで開き直した利用者が素通りする。

**注**: 8 が必要なのは、**遷移を止めるだけでは中身が見えてしまう**ためである。1 により判定が済むまで振り替えないため、その間に保護された経路の内容が画面に出る。ガードの担当を「遷移の制御」ではなく**「到達の制御」**とする。

**注**: 7 により、ガードは体験のための仕組みであって防御ではない。**防御は組み込み側のアクセス制御が担う。ガードがあることを理由にセキュリティルールを緩めない**（`auth-store-and-screens` 要件と同じ）。

### Requirement 5: サインイン後の戻り先

**Objective:** 利用者として、開こうとしたページへサインインの後にそのまま進みたい。入り口から辿り直す手間をなくすため

#### Acceptance Criteria

1. When 到達ガードがサインインの経路へ振り替えたとき, the 到達ガード shall 振り替えの原因になった経路を戻り先として保持する
2. When 利用者が組み込み先の求める条件を満たしたとき, the 到達ガード shall 保持している戻り先へ遷移し、その戻り先を破棄する
3. If 戻り先が保持されていないとき, then the 到達ガード shall 既定の行き先へ遷移する
4. If 保持しようとする戻り先が組み込み先と同一のオリジンでないとき, then the 到達ガード shall その戻り先を用いず、既定の行き先を用いる
5. While 利用者がメールアドレスの確認を終えるまでのあいだ, the 到達ガード shall 保持している戻り先を失わない
6. The 到達ガード shall 認証の経路そのものを戻り先として保持しない

**注**: 4 は、外部の URL を戻り先に仕込むことで、組み込み先のサインイン画面を踏み台にした誘導が成立することを防ぐための要求である（→ 筆者が置いた仮定 4）。

**注**: 6 は、サインインの経路をサインイン後の行き先にして遷移が止まらなくなることを防ぐためである。

### Requirement 6: 配布の形と組み込みの手引き

**Objective:** 組み込み側の開発者として、経路を用意して設定を書けば動く状態にしたい。何をどこへ置くのかを毎回推測しないため

#### Acceptance Criteria

1. The 認証ライブラリ shall 組み込み側が用意する経路と、そこへ置くものを README で示す
2. The 認証ライブラリ shall 到達ガードを有効にする箇所と書き方を README で示す
3. The 認証ライブラリ shall 各画面を実際に操作して確かめられるショーケースを、SvelteKit の経路として備える
4. The ショーケース shall 組み込み側の書き方の実例として機能し、README と食い違わない
5. The 認証ライブラリ shall ショーケースのコードを配布物に含めない

**注**: 3 は、ショーケースが画面の切り替えを自前で持つ形をやめることを意味する。自前の切り替えを残すと、**ライブラリの遷移とガードを通らない経路でしか確かめられない**。

### Requirement 7: 変更の記録と、組み込み側へ返す事項

**Objective:** 開発者として、この方針転換の理由を後から辿れるようにしたい。同じ議論を繰り返さないため

#### Acceptance Criteria

1. The 認証ライブラリ shall `tech.md`「SvelteKit に依存しない」を、SvelteKit を前提とする方針とその理由へ置き換える

**注**: 2 の書き換えでは**番号を動かさない**。既存の項目の文言を書き換える（→ `conventions.md`）。
