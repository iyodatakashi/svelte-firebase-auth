# 実装ギャップ分析

## 対象と前提

対象は `multi-account-auth` の要件定義書と現行リポジトリの差分である。本分析を作成した時点では、要件は生成済みで `approvals.requirements.approved` は `false` だった。ここでは実装方法を確定せず、設計で解くべき差分と選択肢を示す。markn のソースはこのワークスペースにないため、実際のユーザーメニューとデータ層の接続は未確認である。

## 現状で使えるもの

- `src/lib/stores/auth.svelte.ts` の `createAuthStore(auth, config)` は渡された `Auth` ごとに状態を持つ。`start` / `stop` で購読を管理し、メールアドレス、確認状態、認証段階を公開する。単一アカウントの認証処理は再利用できる。
- `src/tests/support/emulator.ts` は、同じテスト用 Firebase プロジェクトに対し、名前を変えた Firebase App と Auth を生成している。ただし、これはテスト間の分離用であり、ブラウザ内で複数アカウントを保持・復元できることの検証ではない。
- `src/lib/components/SignIn.svelte` は入力・認証・エラー表示を持ち、`onCompleted` もある。`src/lib/messages/` に日本語と英語の文言がある。
- `src/lib/models/auth/authGuard.ts` と `src/lib/components/AuthGate.svelte` は、単一ストアの認証段階、保護された内容の抑止、戻り先の保持を扱う。
- `src/routes/` のショーケースと `src/tests/e2e/showcase.e2e.ts` は、認証の経路と Auth エミュレータを用いた操作検証の土台になる。

## 統合上の注意点

1. **認証の初期化責務。** 現行方針は、組み込み側が Firebase を初期化して `Auth` を渡すこと。複数アカウントでは、アカウントごとに独立した Auth を用意し、その名前と寿命を管理する必要がある。ライブラリが名前付き App を作るか、組み込み側から生成手段または Auth 群を受け取るかで公開契約が変わる。`src/tests/support/emulator.ts` は前者の技術的な出発点だが、配布 API の先例ではない。
2. **選択とデータアクセス。** 現行 `AuthStore` は内部の `Auth` を公開しない。markn が選択中の利用者の権限でデータを読むための接続方法と、選択変更時に旧アカウントの購読や画面上のデータを切り替える境界が必要。Firestore の操作自体はこのライブラリの担当ではない。
3. **ガードの入力。** 現行 `AuthGate` は1つの `AuthStore` を props で受け取り、`AuthStage` は `unresolved` / `signed-out` / `email-unverified` / `ready` の4値。保持アカウントはあるが選択されていない状態を表せない。現行ガードは保護された子画面を描画しないため、markn の選択ダイアログがその内側にあるとログアウト時に一緒に消える。ダイアログを常に表示・操作できる接続が必要。
4. **追加ログインの画面。** 現行 `SignIn` は外枠を持たないが、登録と再設定に `goto` を使う。今回合意した「中身のみを組み込み側のダイアログまたはページに置く」契約には、成功通知、キャンセル、登録・再設定への導線の扱いを含めて考える必要がある。ダイアログの外枠と開閉は markn 側。
5. **保存領域と状態の寿命。** `AuthGate` は戻り先を `sessionStorage` に保存している。要件はログイン状態をブラウザ再起動後も保持し、選択をタブ単位で維持しながら、新しいタブは最後に開いたアカウントを初期選択する。アカウントの識別子・復元順序・削除後の保存情報・保存失敗時の表示を揃える必要がある。`structure.md` はブラウザ保存領域への直接アクセスを `components/` に限るため、状態管理層での復元との整合も設計課題になる。
6. **単一アカウント利用者への影響。** `createAuthStore` と5画面の契約を保ったまま機能を追加できるか、`AuthGate` の入力や経路設定を変更する必要があるかを確認する。既存 Auth にログイン済みでも複数アカウント用の保存記録はないため、初回移行時に一覧への採用だけでなく選択と最後に開いた ID の記録が必要になる。公開型と画面 props の変更は既存の組み込み先への影響が大きい。

## 要件を設計前に照合する点

- **追加後の自動選択と未保存データ。** 要件 2.2–2.3 の自動選択は依頼者が決定済み。markn が未保存データを確認するなら、追加ログインの開始前または認証の実行前に済ませ、成功後は新しいアカウントへ切り替える必要がある。
- **標準の一覧画面の有無。** 要件 1.4–1.5、5.1、7.3 は「アカウント画面」を要求する一方、合意済みの組み込み形式は markn がメニューを作り、ライブラリの一覧画面を必須にしない。ライブラリが任意の一覧画面も提供するのか、これらの受け入れ基準を組み込み側の表示に関する期待へ改めるのか、整理が必要。
- **未選択時の表示と到達制御。** 選択中アカウントからのログアウト後、他のログイン状態が残れば markn が選択ダイアログを表示することは依頼者が決定済み。ガードが保護された内容を抑止してもダイアログを表示できる接続を設計する。ログイン状態の失効・復元失敗でも同じ選択導線を使うかは未承認の提案。
- **ログアウト失敗の扱い。** 要件 5.6 は部分成功と再試行を求める。現行 API では失敗を検知できず、指定アカウントのログアウト結果を表す契約が要る。
- **追加フォームの導線。** 要件 2.6–2.8 は登録・再設定まで含むが、ページとダイアログのどちらでも使えるようにしたときの遷移・閉じ方は未決定。

## 実装アプローチの選択肢

### A. 既存ストアと画面を拡張する

`AuthStore` に一覧・選択・対象指定ログアウトを加え、`SignIn` に追加ログイン用の表示を加える。新しい抽象は少ないが、単一アカウント用 API の責務が増え、既存利用者への影響と、ページ遷移を持つ画面の分岐が大きい。

### B. 複数アカウント用の独立した公開面を作る

独立した管理機能と追加ログインの中身のみのコンポーネントを作り、既存の単一ストアと画面を内部で再利用する。既存契約は保ちやすく、markn のメニューは管理機能を直接使える。一方、選択中アカウントを `AuthGate` と既存画面へ渡す方法が二重になりやすい。

### C. 新しい管理機能を中心に、必要な接続点だけ既存機能を拡張する

一覧・選択・復元・対象指定ログアウトを独立した管理機能に置き、既存の認証ストアや画面は再利用する。`AuthGate` と追加ログインの表示には必要な接続だけを加える。markn のメニューと単一アカウントの既存契約を両立しやすいが、管理機能と既存ストアの寿命、経路、選択変更の同期を明確にする必要がある。

現時点では **C を設計検討の第一候補**とする。これは実装決定ではなく、上の要件の未決事項と Firebase の実挙動を確かめたうえで選ぶ。

## 規模・リスクと設計へ渡す調査

- **規模：L（1–2週間程度の目安）**。認証状態、UI、到達ガード、復元、複数タブ、公開 API、ショーケースにまたがる。
- **リスク：高**。名前付き Auth の永続化、選択変更と非同期操作の競合、旧アカウントのデータが残ること、単一アカウント利用者への影響が主要なリスク。
- **Research Needed：Firebase Auth。** 同一プロジェクトの名前付き App / Auth で、アカウントごとの永続化、再起動後の復元、ログアウトの独立性、別タブでの反映を Auth エミュレータとブラウザで確認する。モックのみを根拠にしない。
- **Research Needed：markn 接続。** 実際のユーザーメニューの配置、保護された画面の外でも使える導線、Firestore 等への認証の渡し方、未保存データの扱いを markn 側で確認する。このワークスペースでは未確認。
- **Research Needed：公開契約。** Auth の生成責務、選択中アカウントの認証情報、失敗の語彙、単一アカウントからの移行方法を設計段階で具体化する。

分析時点ではコード変更もテスト実行も行っていない。既存テストの有無とコード上の振る舞いを調べた結果であり、新しい複数アカウントの動作を検証済みとするものではない。
