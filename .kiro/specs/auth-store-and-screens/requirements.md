# Requirements Document

## Project Description (Input)

Firebase Authentication のメールアドレスとパスワードによる認証について、認証ストアと認証の画面一式を `@14ch/svelte-firebase-auth` として提供する。組み込み側は同じ認証の処理と画面を書き直さずに済む状態にする。

### 対象

- **認証ストア** — `createAuthStore(auth, config)`。サインイン状態・利用者・正規化済みのメールアドレス・メールアドレスの確認状態を公開し、サインイン／登録／サインアウト／パスワードの変更／パスワードの再設定／確認メールの送信を行う
- **認証の画面** — サインイン・登録・**メールアドレスの確認待ち**・パスワードの変更・パスワードの再設定の5画面
- **エラーの語彙** — Firebase のエラーコードを、利用者への案内が分かれる粒度へ畳んだ判別可能な共用体で返す（例外を投げない）
- **文言の差し替え** — 既定の日本語を同梱し、組み込み側が項目単位で差し替えられる
- **`normalizeEmail`** — メールアドレスの正規化をライブラリが持ち、公開する

### 決定: メールアドレスの確認待ち画面はライブラリが持つ

steering（product.md「まだ決めていないもの」）で最初の spec に委ねられていた点。**ライブラリが持つ。**

- 確認待ちの状態は Firebase Authentication の利用者が持つ事実であり、アプリに依らない
- 画面の中身（送信先のメールアドレスの提示・迷惑メールフォルダの案内・確認メールの再送・別のメールアドレスでの登録し直し・サインアウト）もアプリに依らない
- 確認の反映には `onAuthStateChanged` では足りず、利用者の状態と ID トークンのクレームの取り直しが要る。この事情は Firebase Auth の性質であってアプリの事情ではないため、ライブラリ側に閉じる

**組み込み側に残るのは到達の判断だけ。** 「確認済みでなければ使わせない」「未確認の利用者をどこへ送るか」はアプリの画面構成の問題であり、ライブラリは持たない。ライブラリは確認済みになったことをコールバックで返し、遷移は組み込み側が行う。

### 最初の組み込み先（markn）で既に書かれている契約

`markn` の `account-self-service` spec（requirements は承認済み、design は生成済みで未承認）に、このライブラリの公開面が `AuthModuleContract` として書かれている。**これは出発点であって制約ではない**が、最初の組み込み先の実需としてここから始める。

- `AuthConfig` — `selfRegistration`（登録の入口を画面に出すか）／`continueUrl`（確認・再設定の完了後に戻る URL）
- `AuthStore` — `user` / `isResolved`（初回の認証状態判定の完了。単調）/ `isLoggedIn` / `email`（正規化済み）/ `isEmailVerified` / `canSelfRegister`、および `signIn` / `signUp` / `signOut` / `changePassword` / `sendPasswordReset` / `sendEmailVerification` / `refreshVerification`
- `AuthErrorKind` — `invalid-credential` / `invalid-email` / `email-already-in-use` / `weak-password` / `requires-recent-login` / `user-disabled` / `too-many-requests` / `unknown`。`AuthResult` は判別可能な共用体
- 画面の props — `store` / `messages?`（項目単位の差し替え）と、画面ごとの完了・遷移要求のコールバック

あわせて満たすべき性質:

- **メールリンクによるサインインを備えない**
- **パスワードの再設定は、そのメールアドレスが登録されているかどうかを示さない**
- **パスワードの変更は、現在のパスワードによる再認証を伴う**
- **登録の成功時はサインイン済みの状態にし、確認メールを送る**
- **認証に関するメールの送信を、組み込み側が別の経路へ差し替えられる形で扱う**（本 spec では Firebase の既定の経路を使い、差し替えの実装は含めない）
- **`AuthErrorKind` の増減は組み込み側の文言に波及する**

### この spec で決めること

- **公開する画面の粒度** — 画面をまるごと渡す形だけで足りるのか、ストアと部品を組み合わせる余地も要るのか。`header` と `messages` で吸収できる範囲を、最初の組み込み（markn）で見極める
- **確認待ち画面の契約** — 確認済みの取り直しをどの周期で行い、いつ止めるか。「別のメールアドレスで登録し直す」をどのコールバックで返すか
- **再送の頻度超過をどう扱うか** — Firebase の `too-many-requests` を利用者への案内へどう畳むか

### 担当しないこと（組み込み側の担当）

- **Firebase の初期化** — `Auth` インスタンスを外から受け取る
- **遷移とルーティング** — `$app/*` を import しない。完了・失敗はコールバックで返す
- **到達ガード** — 未サインイン／未確認の利用者をどこへ送るか
- **Firestore とアクセス制御** — 確認済みをアクセス制御で要求するのは組み込み側
- **メールの送信経路と到達性の運用** — 送信元ドメイン・SPF / DKIM / DMARC・テンプレート
- **既存利用者の移行と運用者の作業**

### 組み込み側（markn）へ返す事項

確認待ち画面をライブラリが持つ決定により、markn 側の design に整合しない箇所が残る。本 spec の承認後に markn 側で扱う。

- `AuthModuleContract` の「4画面」という記述（`VerifyEmailScreenProps` を含めて5画面になる）
- markn 側の `VerifyEmailPage` — 他の画面と同じく、モジュールの画面に対する薄いアダプタになる
- 主語が **the markn** となっている確認待ち画面の要件（3-5、3-6、6-4〜6-7）— 画面の実体は **the 認証モジュール** に移る
- **公開する画面の名前から `Screen` を落とした**（`SignInScreen` → `SignIn`、`SignInScreenProps` → `SignInProps`、共通の基底は `AuthBaseProps`）。markn の `AuthModuleContract` に書かれた名前は、こちらの名前に合わせる

## Introduction

Firebase Authentication を使う Svelte アプリケーションのために、**認証の処理と画面**を1つのパッケージにまとめる。組み込み側に残すのは、**遷移と到達の判断**だけにする。

これはライブラリであってアプリケーションではない。最初の組み込み先は `markn` だが、markn 専用ではない。**組み込み側の判断をライブラリの内部に抱えない。** ある特定のアプリだけに必要な分岐が現れたら、設定・コールバック・文言の差し替えとして外へ出す。

### EARS の主語

この spec の主語は3種類ある。組み込み側アプリケーションの振る舞いは本 spec の対象ではなく、主語にも現れない。

- **the 認証ライブラリ** — パッケージとして公開する面全体の性質。設定・型・語彙・配布の形
- **the 認証ストア** — `createAuthStore` が返すもの。認証状態の保持と Firebase Auth への操作
- **the サインイン画面 / 登録画面 / 確認待ち画面 / パスワード変更画面 / パスワード再設定画面** — 個々の画面。**the 各画面** は5画面すべてに共通する要求を指す

### 依頼者が決めたこと

- **メールアドレスの確認待ち画面はライブラリが持つ。** 画面の中身はアプリに依らず、到達の判断だけが組み込み側に残る
- **画面までライブラリに含める。** 各プロジェクトで書き直さない
- **対象はサインイン・登録・確認待ち・パスワードの変更・パスワードの再設定。** メールアドレスの変更は含めない
- **メールリンクによるサインインを備えない**
- **メールの送信は Firebase の既定の経路を使う。** 自前の配信経路へは移さないが、移せる余地は残す
- **自由登録の可否は設定で切り替える。** 招待の仕組みは作らない
- **メールアドレスの確認を求めるかどうかも設定で切り替える。** 確認を必須にしていないプロジェクトにも組み込めるようにする（2026-08-23 の依頼）

### 筆者が置いた仮定（未承認）

依頼者の指示に含まれておらず、要件を書くために筆者が置いた仮定。承認されていないため、必要なら差し替えてよい。

1. **公開する画面の粒度は、画面をまるごと渡す形だけとする**（要件 9-1）。ストアと部品を組み合わせる余地は今回は公開しない。組み込み側の差異は `header` と文言の差し替えで吸収する。公開面は小さいほど破壊的変更が減り、足りなければ後から足せるが、出したものは引っ込められないため
2. **確認済みの取り直しは、確認待ち画面が表示されている間だけ自動で行う**（要件 5-5、5-6）。常時の取り直しは通信の負担になり、画面を離れた後も続くのは漏れである
3. **再送や再設定の要求が Firebase に受け付けられなくなったときは、間隔を空けるよう示し、その操作を一時的に受け付けない**（要件 5-8、7-6）。押せる状態のまま失敗し続けると、利用者は原因が分からない
4. **「別のメールアドレスで登録し直す」はサインアウトを伴い、その後の遷移は組み込み側へ返す**（要件 5-9）。サインアウトまではアプリに依らないが、どの画面へ送るかはアプリの構成の問題であるため
5. **パスワードの変更には現在のパスワードの入力を求める**（要件 6-1）。Firebase の再認証の要求に応えると同時に、離席中の端末で変更される経路を塞ぐ
6. **再設定用のリンクを開いた先（新しいパスワードの入力）は、Firebase の既定のアクションハンドラに委ねる**（要件 7 の注）。自前のアクションハンドラ画面を持たない
7. **確認メールのリンクを開いた先も同様に Firebase の既定のアクションハンドラに委ねる**（要件 5 の注）。ライブラリは取り直しによって確認済みを検知する

## Boundary Context

- **In scope**: 認証ストア（状態と操作）、5画面（サインイン・登録・確認待ち・パスワードの変更・パスワードの再設定）、エラーの語彙、文言の差し替え、メールアドレスの正規化、自由登録の可否の設定、確認・再設定の戻り先の設定、パッケージの公開面とショーケース
- **Out of scope**: Firebase の初期化、遷移とルーティング、到達ガード、Firestore とアクセス制御、自前のアクションハンドラ画面、自前のメール配信経路の実装、メールの到達性の運用（SPF / DKIM / DMARC・テンプレート）、既存利用者の移行と運用者の作業、メールリンクによるサインイン、メールアドレスの変更、外部の認証プロバイダ、二要素認証、アカウントの削除
- **後続で加えうる（対象外ではない）**: 外部の認証プロバイダ（Google / Apple などのソーシャルログイン）、メールの送信経路の差し替えの実装、ストアと部品を組み合わせる公開面
- **Adjacent expectations**:
  - **`markn` / `account-self-service`** — 最初の組み込み先。本 spec の公開面がそちらの `AuthModuleContract` に対応する。確認待ち画面の所在の変更を markn 側へ返す
  - **`@14ch/svelte-ui`** — 画面はこのライブラリの部品とトークンで組む。足りない部品はそちら側の課題として扱う
  - **Firebase Authentication** — パスワードの強度・頻度の制限・アクションハンドラの挙動はこのサービスが定める。ライブラリはそれを畳んで伝える

## Requirements

### Requirement 1: ライブラリとしての公開面と組み込みの制約

**Objective:** 開発者として、認証の処理と画面を複数のプロジェクトから同じ形で使いたい。同じものを書き直さず、特定のアプリの都合をライブラリへ持ち込まないため

#### Acceptance Criteria

1. The 認証ライブラリ shall Firebase の認証インスタンスを組み込み側から受け取り、自身では Firebase の初期化を行わない
2. The 認証ライブラリ shall SvelteKit のルーティングを用いて遷移を自身で行い、認証の経路を組み込み側の設定として受け取る
3. The 認証ライブラリ shall 認証以外の Firebase の機能に触れない
4. The 認証ライブラリ shall 組み込み側が依存してよい面（生成関数・画面・型・純関数）を単一の公開面から提供し、深い import を組み込み側に強いない
5. The 認証ライブラリ shall 公開する値に対応する型を公開面から提供し、組み込み側が型を書けない状態にしない
6. The 認証ライブラリ shall メールリンクによるサインインを備えない
7. The 認証ライブラリ shall メールアドレスの正規化を提供し、組み込み側が共有の照合とアクセス制御に用いる値と同じ値を得られるようにする
8. The 認証ライブラリ shall 認証に関するメールの送信を単一の箇所に閉じ、組み込み側が別の送信経路へ差し替えられる余地を残す
9. Where 組み込み側が確認と再設定の完了後の戻り先を設定で指定したとき, the 認証ライブラリ shall その戻り先を、送信する確認メールと再設定メールに反映する
10. The 認証ライブラリ shall グローバルな状態を持たず、同一の実行環境で複数の認証ストアを生成できる状態にする
11. The 認証ライブラリ shall メールアドレスの確認を求めるかどうかを組み込み側の設定として受け取り、求めない場合は登録の後に確認メールを送らない

**注**: 11 は、メールアドレスの確認を必須にしていないプロジェクトにも組み込めるようにするための要求である。**この設定が制御するのは確認メールを自動で送るかどうかだけ**であり、到達の判断（確認済みでなければ使わせない）は設定の有無によらず組み込み側の担当である（→ 要件 5 の注）。`sendEmailVerification` は設定によらず呼べる。

**注**: 2 は `sveltekit-routing-and-guard` が書き換えた。もとは「特定のアプリケーションフレームワークのルーティングに依存せず、遷移を自身で行わない」だった。**その規則が引かれた理由は「SvelteKit 以外のアプリで使えなくなる」ことだったが、依頼者の判断により組み込み先は SvelteKit に限られると決まり、前提そのものが失われた。** framework 非依存は利用者が実在しない抽象であり、対価として組み込み先ごとに 13 本のコールバックの配線と段階から遷移への対応づけを書き直すことになっていた。

**注**: 8 は将来の差し替えのための要求であり、本 spec では Firebase の既定の経路を使う。差し替えの実装も、そのための設定も含めない。**省略可能な設定を後から足すことは破壊的変更ではない**ため、余地を残すために今から公開面へ設定を置く必要は無い。守るべきは、送信の呼び出しが画面へ散らばらないことである。

### Requirement 2: 認証ストアが公開する状態

**Objective:** 組み込み側の開発者として、到達の判断に必要な状態を1箇所から読みたい。同じ判定を各アプリで書き直さず、判定のずれを生まないため

#### Acceptance Criteria

1. The 認証ストア shall 現在の利用者と、サインインしているかどうかを公開する
2. The 認証ストア shall 初回の認証状態の判定が完了したかどうかを公開する
3. When 初回の認証状態の判定が完了したことを一度示したとき, the 認証ストア shall それ以降その状態を未完了へ戻さない
4. The 認証ストア shall 現在の利用者のメールアドレスを、正規化した形で公開する
5. The 認証ストア shall 現在の利用者のメールアドレスが確認済みかどうかを公開する
6. The 認証ストア shall 自由登録が許可されているかどうかを公開する
7. When Firebase Auth の認証状態が変化したとき, the 認証ストア shall 公開している状態を追随させる
8. When 確認状態の取り直しが要求されたとき, the 認証ストア shall 利用者の状態と ID トークンのクレームを取り直したうえで、確認済みかどうかを返す
9. If 確認状態の取り直しが完了する前に同じ要求が重ねて行われたとき, then the 認証ストア shall 追加の問い合わせを行わず、実行中の要求の結果を共有する
10. The 認証ストア shall 確認状態の取り直しを、確認待ち画面以外からも要求できる手段として公開する
11. The 認証ストア shall 認証状態の購読を開始する手段と停止する手段を提供し、停止した後は公開している状態を更新しない
12. The 認証ストア shall 認証の段階（初回の判定が未了・未サインイン・確認待ち・通過）を単一の値として公開し、組み込み側が同じ判定を書き直さずに到達を判断できるようにする

**注**: 3 は、判定が済むまで「サインインしていない」と「まだ分からない」を組み込み側が区別できるようにするための要求である。区別できないと、判定の完了前に未サインインとして扱う誤りが起きる。

**注**: 8 が必要なのは、`onAuthStateChanged` がメールアドレスの確認の完了では発火しないためである。

**注**: 12 の判定は、公開している状態（2-2、2-5、要件 1-11 の設定）の組み合わせだけで決まり、アプリの知識を必要としない。**どの組み込み先でも同じ判定になるため、ライブラリが持つ。** その段階で何をするか（どこへ遷移するか）は組み込み側の担当であり、ライブラリは行わない（→ 要件 1-2）。

**注**: 11 は、生成できて終わらせられない対を作らないための要求である。複数生成できる以上（要件 1-10）、捨てたストアの購読が生き続けると、誰も見ていない状態を書き換え続ける漏れになる。

### Requirement 3: サインインとサインアウト

**Objective:** 利用者として、メールアドレスとパスワードでアプリに入りたい。登録した資格情報だけで、いつもの手順で使い始められるため

#### Acceptance Criteria

1. When 利用者がメールアドレスとパスワードを入力してサインインを実行したとき, the 認証ストア shall その資格情報で認証を行い、成功したらサインイン済みの状態にする
2. If メールアドレスまたはパスワードが誤っているとき, then the サインイン画面 shall どちらが誤っているかを示さずに、資格情報が誤っていることを利用者に示す
3. If サインインが失敗したとき, then the サインイン画面 shall 入力した内容を失わせない
4. While サインインの処理中であるとき, the サインイン画面 shall 処理中であることを利用者に示し、同じ操作の重複した実行を受け付けない
5. When サインインが完了したとき, the サインイン画面 shall 完了したことを組み込み側へ通知する
6. When 利用者がサインアウトを実行したとき, the 認証ストア shall サインインしていない状態にする
7. Where 自由登録が許可されているとき, the サインイン画面 shall 登録を要求する手段を提供し、その要求を組み込み側へ通知する
8. Where 自由登録が許可されていないとき, the サインイン画面 shall 登録を要求する手段を提供しない
9. The サインイン画面 shall パスワードの再設定を要求する手段を提供し、その要求を組み込み側へ通知する

**注**: 2 は、登録済みのメールアドレスを外部から探り当てられないようにするための要求である。

### Requirement 4: ユーザー登録と、自由登録の可否

**Objective:** 利用者として、自分でアカウントを作って使い始めたい。運用者にアカウントの作成を依頼する手間をなくすため

#### Acceptance Criteria

1. When 利用者がメールアドレスとパスワードを入力して登録を実行したとき, the 認証ストア shall そのメールアドレスのアカウントを作成し、サインイン済みの状態にする
2. Where メールアドレスの確認を求める設定であるとき, when アカウントの作成が完了したとき, the 認証ストア shall そのメールアドレス宛に確認メールを送る
3. If 入力されたメールアドレスが既に登録されているとき, then the 登録画面 shall 既に使われていることを利用者に示し、パスワードの再設定へ導く
4. If 入力されたパスワードが Firebase の要求する強度を満たさないとき, then the 登録画面 shall その理由を利用者に示し、入力し直せる状態を保つ
5. If 登録が失敗したとき, then the 登録画面 shall 失敗したことを利用者に示し、入力した内容を失わせない
6. When 登録が完了したとき, the 登録画面 shall 完了したことを組み込み側へ通知する
7. The 登録画面 shall サインインへ戻る手段を提供し、その要求を組み込み側へ通知する
8. The 認証ライブラリ shall 自由登録の可否を組み込み側の設定として受け取り、画面の入口の有無に反映する

**注**: 8 が制御するのは画面の入口だけである。登録の API そのものは Firebase 側の設定でしか塞げず、両方を揃えるのは組み込み側の運用（→ markn 要件 2-8）。ライブラリは画面の入口だけを担う。

### Requirement 5: メールアドレスの確認と、確認待ちの画面

**Objective:** 利用者として、登録の直後に何をすればよいかが分かり、確認が済んだら待たされずに先へ進みたい。メールが届かないときにも行き止まりにならないため

#### Acceptance Criteria

1. The 認証ストア shall 現在の利用者のメールアドレス宛に確認メールを送る手段を提供する
2. The 確認待ち画面 shall 確認メールの送信先のメールアドレスを利用者に示す
3. The 確認待ち画面 shall 確認メールが迷惑メールに分類されることがあることと、迷惑メールフォルダを確認するよう利用者に示す
4. The 確認待ち画面 shall 確認メールを再送する手段を利用者に提供する
5. While 確認待ち画面が表示されているとき, the 確認待ち画面 shall 利用者の操作を求めずに確認状態の取り直しを繰り返す
6. When 確認待ち画面が表示されなくなったとき, the 確認待ち画面 shall 確認状態の取り直しを停止する
7. When 取り直しの結果メールアドレスが確認済みになったとき, the 確認待ち画面 shall 確認済みになったことを組み込み側へ通知する
8. If 確認メールの再送が短時間に繰り返されて受け付けられなくなったとき, then the 確認待ち画面 shall 間隔を空けるよう利用者に示し、再送の操作を一時的に受け付けない
9. The 確認待ち画面 shall 別のメールアドレスで登録し直す手段を提供し、サインアウトしたうえでその要求を組み込み側へ通知する
10. The 確認待ち画面 shall サインアウトする手段を提供し、その要求を組み込み側へ通知する

**注**: 確認メールのリンクを開いたときの処理は Firebase の既定のアクションハンドラが行い、ライブラリはその画面を持たない。5 の取り直しにより、**別の端末で確認を済ませた場合にも待機側へ反映される**。

**注**: 「確認済みでなければ使わせない」という判断と、確認待ち画面をいつ表示するかは組み込み側の担当である。ライブラリは画面と検知だけを持つ。

### Requirement 6: パスワードの変更

**Objective:** 利用者として、自分のパスワードを自分で変更したい。運用者に依頼せず、漏洩の疑いや定期的な変更に対処するため

#### Acceptance Criteria

1. When 利用者が現在のパスワードと新しいパスワードを入力して変更を実行したとき, the 認証ストア shall 現在のパスワードによる再認証を行ったうえで新しいパスワードを設定する
2. If 入力された現在のパスワードが誤っているとき, then the パスワード変更画面 shall 現在のパスワードが違うことを利用者に示し、新しいパスワードを設定しない
3. If 新しいパスワードが Firebase の要求する強度を満たさないとき, then the パスワード変更画面 shall その理由を利用者に示し、入力し直せる状態を保つ
4. When パスワードの変更が完了したとき, the 認証ストア shall サインイン状態を保つ
5. When パスワードの変更が完了したとき, the パスワード変更画面 shall 完了したことを利用者に示し、組み込み側へ通知する
6. If パスワードの変更が失敗したとき, then the 認証ストア shall 変更前のパスワードを有効なまま保つ
7. If サインインしていない状態で変更が要求されたとき, then the 認証ストア shall 失敗として返し、Firebase Auth への問い合わせを行わない
8. The パスワード変更画面 shall 変更を取りやめる手段を提供し、その要求を組み込み側へ通知する

### Requirement 7: パスワードの再設定

**Objective:** パスワードを忘れた利用者として、自分で再設定して使い続けたい。アカウントを作り直したり運用者に依頼したりせずに済ませるため

#### Acceptance Criteria

1. When 利用者がメールアドレスを入力して再設定を要求したとき, the 認証ストア shall そのメールアドレス宛に再設定用のメールを送る
2. When 再設定の要求を受け付けたとき, the パスワード再設定画面 shall そのメールアドレスが登録されているかどうかを利用者に示さない
3. When 再設定の要求を受け付けたとき, the パスワード再設定画面 shall メールを送ったことと、迷惑メールフォルダも確認するよう利用者に示す
4. When 再設定の要求が完了したとき, the パスワード再設定画面 shall 完了したことを組み込み側へ通知する
5. The パスワード再設定画面 shall サインインへ戻る手段を提供し、その要求を組み込み側へ通知する
6. If 再設定の要求が短時間に繰り返されて受け付けられなくなったとき, then the パスワード再設定画面 shall 間隔を空けるよう利用者に示し、要求の操作を一時的に受け付けない

**注**: 2 は、登録済みのメールアドレスを外部から探り当てられないようにするための要求である。登録の有無にかかわらず同じ応答を返す。

**注**: 再設定用のリンクを開いた先（新しいパスワードの入力・リンクの期限切れや使用済みの扱い）は Firebase の既定のアクションハンドラが行う。ライブラリはその画面を持たない（→ 筆者が置いた仮定 6）。

### Requirement 8: エラーの語彙と、結果の返し方

**Objective:** 組み込み側の開発者として、失敗の種類を自分の文言へ対応づけたい。Firebase の語彙に依存せず、網羅の漏れを型で気づけるため

#### Acceptance Criteria

1. The 認証ライブラリ shall 認証に関する操作の失敗を例外として投げず、成功と失敗を判別できる戻り値で返す
2. The 認証ライブラリ shall Firebase のエラーコードを、利用者への案内が分かれる粒度の語彙へ畳んで返す
3. The 認証ライブラリ shall Firebase のエラーコードをそのまま組み込み側へ透過させない
4. If 対応する語彙が無いエラーが発生したとき, then the 認証ライブラリ shall その他として扱い、原因を示す詳細を添えて返す
5. The 各画面 shall 返された語彙に対応する案内を利用者に示し、利用者が操作をやり直せる状態を保つ
6. The 認証ライブラリ shall エラーの語彙を公開面の型として提供する

**注**: 語彙の増減は組み込み側の文言に波及するため、破壊的変更として扱う（→ `structure.md`「公開面」）。

### Requirement 9: 画面の契約と、文言の差し替え

**Objective:** 組み込み側の開発者として、画面を書かずに認証を組み込みたい。自分のアプリの見た目と遷移に馴染ませつつ、マークアップを持たずに済ませるため

#### Acceptance Criteria

1. The 認証ライブラリ shall 各画面を、組み込み側がそのまま配置して使える単位で提供する
2. The 各画面 shall 認証ストアを props で受け取り、Firebase Auth を直接呼ばない
3. The 各画面 shall 段階を変えない導線の遷移を自身で行い、完了と遷移の要求を組み込み側へ返すコールバックの props を持たない
4. The 認証ライブラリ shall 画面に出す既定の文言を日本語で同梱する
5. Where 組み込み側が文言を指定したとき, the 認証ライブラリ shall 指定された項目だけを差し替え、指定のない項目には既定の文言を用いる
6. The 各画面 shall 題字（見出し）などのページの要素を持たず、入力欄・操作・提示だけを描画する
7. The 各画面 shall 意匠の値を `@14ch/svelte-ui` のトークンから参照し、独自のパレットを持たない
8. The 各画面 shall 画面全体を占めることを前提とした外形を持たず、組み込み側のレイアウトに置ける形にする
9. The 各画面 shall ブラウザ標準のダイアログを用いず、`@14ch/svelte-ui` の部品で利用者への提示を行う

**注**: 3 は `sveltekit-routing-and-guard` が書き換えた。もとは「遷移を自身で行わず、完了と遷移の要求をコールバックで組み込み側へ返す」だった。**理由は要件 1-2 と同じ**（→ 要件 1 の注）。段階を変える完了（サインイン・登録・確認・サインアウト）の遷移は到達の制御が行うため、画面が持つのは段階を変えない導線だけである。**この変更で画面の props からコールバックが消え、画面ごとの props の型も `AuthBaseProps` へ一本化された。破壊的変更として扱う。**

**注**: 6 は `sveltekit-routing-and-guard` が書き換えた。もとは「組み込み側が画面の上部へ自身の名乗りを差し込める手段を提供する」であり、`header?: Snippet` の props がこれに当たっていた。**依頼者の判断により、題字も名乗りもページの要素であり、画面を置く側の担当と決まった。** 差し込み口を持つと、見出しの階層とレイアウトの決定がライブラリと組み込み側に分かれる。`header` の props と、各画面が持っていた題字の文言（`signInTitle` ほか5項目）を削除した。**破壊的変更として扱う。**

**注**: 1 は、画面をまるごと渡す形だけを公開することを意味する（→ 筆者が置いた仮定 1）。ストアと部品を組み合わせる余地は本 spec では公開しない。

### Requirement 10: 配布の形と、組み込みの手引き

**Objective:** 組み込み側の開発者として、パッケージを入れてすぐ動く状態にしたい。`.svelte` のまま配布されるパッケージ特有の設定で詰まらないため

#### Acceptance Criteria

1. The 認証ライブラリ shall 配布物に、組み込み側が必要とする設定（依存の事前バンドルの除外と `svelte` の重複解決）を README で示す
2. The 認証ライブラリ shall ショーケースのコードを配布物に含めない
3. The 認証ライブラリ shall 各画面を実際に操作して確かめられるショーケースを備える
4. The ショーケース shall Firebase の初期化と遷移の書き方の実例として機能し、README と食い違わない
5. The 認証ライブラリ shall `firebase` / `svelte` / `@14ch/svelte-ui` を peer の依存として宣言し、実体を自身で抱えない

**注**: 1 の設定を欠くと `svelte` の実体が二重になり、描画に失敗する（→ `tech.md`「パッケージの配布」）。
